# PRD: 画像精度の改善（曲ジャケット・アニメ作品）

- 作成日: 2026-10-30 ｜ ステータス: draft ｜ 作成: /write-prd（要件は /grill-me で 2026-10-30 に合意）

## 1. 背景（なぜ今これをやるのか）

- 画像は「表示されたときに外部 API で探し、採用できたものだけ DB に保存」する方式。DB に画像がある件数は、曲 547 / 230,965、アニメ 390 / 10,268（2026-10-27 実測）。大半は誰も開いていないため未取得
- オーナーが「違う画像が付く」「NO IMAGE が多い」の両方を問題視している
- 判定は 2026-07 に Dice 類似度と人気度タイブレークを入れたが、検証は 61 件のみで、カテゴリ別の誤り率・付く率は測っていない
- 一致しなかった結果を保存しないため、同じ曲を表示するたびに外部 API を呼び直している（ROADMAP #19）

## 2. 目的（1文で。測定可能な成功指標つき）

曲ジャケット（アニソン・VTuber・ゲーム曲）とアニメ作品の画像について、**抜き取り検査で誤り率 1% 以下を保ったまま、画像が付く率を修正前より上げ**、事前の一括取得で初回表示から画像が出る状態にする。

- 方針「誤った画像より NO IMAGE」は維持する

## 3. ユーザー（誰が・どんな状況で・何のために使うか）

- **サイトの利用者**（ログインの有無を問わない）：検索結果・詳細ページ・リスト・シェア画像で曲や作品を見分ける
- **オーナー**：試し実行の結果を確認して本番反映を承認する。秘密情報（API キー等）を GitHub に登録する

## 4. 機能要件（優先度つき）

| # | 機能 | 優先度 | 受け入れ条件（検証可能な形で） |
|---|---|---|---|
| F1 | 現状測定：アニソン・VTuber・ゲーム曲・アニメ作品から各 300 件を無作為抽出し、今の判定で誤り率と付く率を出す | Must | カテゴリごとに「付いた／付かない」「付いた中の誤り件数」が表で出る。DB は一切変更しない |
| F2 | 判定の改善（曲）：曲名・アーティスト名の照合を強め、アニソンは作品名も手がかりにする | Must | F1 と同じ抽出で再測定し、各カテゴリの誤り率 1% 以下、付く率が F1 より高い |
| F3 | 取得元の追加：VTuber は YouTube の動画サムネイル（正方形に切り抜いて表示）、ゲーム曲はジャケットが無ければゲームのパッケージ画像で代用 | Must | VTuber・ゲーム曲の付く率が F1 より高く、誤り率 1% 以下 |
| F4 | 判定の改善（アニメ作品）：AniList の候補・照合を見直す | Must | アニメ作品の誤り率 1% 以下、付く率が F1 より高い |
| F5 | 既存の保存済み画像の再検査：曲 547・アニメ 390 件を新しい判定で見直す | Must | 差し替え・削除の候補一覧（変更前後の画像つき）を出し、オーナーの GO 後にだけ本番へ反映 |
| F6 | 一括取得（試し実行）：各カテゴリ数百件を DB を変えずに処理し、結果一覧を出す | Must | 一覧（曲名・採用画像・取得元・スコア）と抜き取り画像をオーナーが確認できる |
| F7 | 一括取得（本番）：GitHub Actions で全件を順に処理し、途中で止まっても続きから再開する | Must | 再実行しても処理済みの曲を API に問い合わせない。オーナーの GO 後に実行 |
| F8 | 一致しなかった結果の記録：「探したが見つからなかった」を保存し、アプリが同じ曲で毎回 API を呼ばないようにする | Should | 記録済みの曲を表示しても外部 API へのリクエストが発生しない（再試行は一定期間後のみ） |
| F9 | アプリ側の判定を一括取得と同じロジックにそろえる | Should | 判定関数を共通化し、単体テストで同じ入力に同じ結果を返す |

## 5. 非機能要件

- **性能**：外部 API の利用条件を守る（iTunes は 1 分に約 20 回を上限の目安とし、それ以下で送る。AniList は 1 分 90 回以下）。アプリの表示は今どおり画像取得を待たない
- **セキュリティ**
  - 一括取得の書き込みは service_role キーで行う。キーは**オーナーが GitHub Secrets に登録**する（AI のコンテキストやログに通さない）
  - anon キーの書き込み範囲は広げない（ROADMAP #4 と逆行させない）
  - YouTube Data API キーもオーナーが登録する
- **可用性**：一括取得は止まっても続きから再開できる。失敗しても本番のアプリには影響しない
- **保守性**：判定ロジックは一括取得とアプリで共通にし、テストを付ける。判定の閾値は 1 か所で管理する

## 6. UI（画面一覧・遷移・ワイヤー参照）

- 既存画面の見た目は変えない（検索結果・詳細・リスト・シェア画像で表示される画像が変わるだけ）
- VTuber のサムネイルは横長なので、表示枠に合わせて中央を正方形に切り抜く（`object-fit: cover`）
- 確認用：試し実行・再検査の結果を、オーナーが見るための一覧（HTML の画像一覧）で出す。本番サイトには載せない

## 7. データ構造（エンティティ・スキーマ・保存先）

- 既存：`songs.image_url`・`anime.image_url`（許可 CDN ドメインの CHECK 制約あり）
- 追加（案）：`songs` と `anime` に次の列
  - `image_source text`：`itunes` / `youtube` / `rawg` / `anilist` など
  - `image_checked_at timestamptz`：最後に探した日時（見つからなかった場合も記録）
- `image_url` の CHECK 制約に YouTube のサムネイル配信ドメイン（`i.ytimg.com`）を追加
- 新しい列は anon / authenticated から更新できないようにする（一括取得の service_role だけが書く）
- マイグレーションを `backend/supabase/` に追加し、`migration_security_baseline.sql` も更新する

## 8. API（エンドポイント・入出力・エラー）

| 取得元 | 用途 | 認証 | 備考 |
|---|---|---|---|
| iTunes Search API | 曲ジャケット | 不要 | 既存。`country=JP` |
| AniList GraphQL | アニメ作品の画像 | 不要 | 既存 |
| YouTube Data API v3 | VTuber 曲の動画サムネイル | API キー | `search.list` は 1 回 100 ユニット（1 日 10,000 ユニット＝100 回）。`youtube_id` 登録済みの曲は API を使わず `i.ytimg.com/vi/{id}/hqdefault.jpg` を使う |
| RAWG | ゲーム曲の代用画像（ゲームのパッケージ） | API キー（既存） | 既存の `games.image_url` があればそれを使う |

- エラー時（429・5xx・タイムアウト）はその曲を「未処理」のまま残し、次回の実行で再試行する。見つからなかった場合だけ `image_checked_at` を記録する

## 9. リスクと対策

| リスク | 影響 | 対策 |
|---|---|---|
| 判定を緩めて付く率を上げると誤りが増える | 方針違反・利用者の誤認 | 誤り率 1% 以下を合格条件にし、F1 と同じ抽出で毎回再測定する |
| 「正解」の判定が人によって揺れる | 誤り率が信用できない | 判定基準（曲名・アーティストが一致、別バージョンは可など）を測定前に文章で決め、境界例は一覧に残す |
| iTunes・YouTube の回数制限 | 一括取得が止まる、IP がブロックされる | 送信間隔を空け、429 のときは待ってから再開。YouTube は 1 日の上限で止める |
| service_role キーの漏えい | DB 全体が操作される | オーナーが Secrets に登録、ログに出さない、ワークフローは最小権限・外部 Action はコミット SHA で固定 |
| 一括で誤った画像を大量に書き込む | 大量の誤表示 | 試し実行 → オーナー GO → 本番。反映前の値を記録し、戻せるようにする |
| ROADMAP #4（キャッシュ書き込みのサーバー移行）との衝突 | 二重実装 | 一括取得は service_role、アプリ側は現状維持。#4 着手時に判定ロジックを共有する |

## 10. マイルストーン（垂直スライスで）

- **M3 の決定（2026-10-31、オーナー承認）**：VTuber・ゲーム曲とも誤り 0%。VTuber は正しい画像 297 件で M1 と同数だが、付く率 99% で頭打ちのため合格扱い。F3 のうち、VTuber の YouTube サムネイル（A2）は見送り（`youtube_id` が全曲空で、検索 API とキーが必要な割に NO IMAGE は 1% だけ）。ゲーム曲の代用画像（A1）は、RAWG では日本語タイトルがほぼ当たらず、VNDB は API が「非商用は無料」・表紙画像の権利が別のため使わない
- **合格条件の読み替え（2026-10-31、オーナー承認）**：「付く率が M1 より高い」は「正しい画像の数が M1 より多い」と読む。M1 の付く率には誤った画像が含まれ、誤りを除くと付く率が下がるため。M2 の結果はアニソンで正しい画像 178 → 182 件、誤り 4.8% → 0%（`tools/image-accuracy/README.md`）

|---|---|---|---|
| M1 | 現状測定 | F1 | カテゴリ別の誤り率・付く率の表と、誤り例の一覧ができる |
| M2 | アニソンの判定改善 | F2・F9（アニソン分） | 再測定で誤り 1% 以下・正しい画像の数が M1 超え（2026-10-31 読み替え。下記） |
| M3 | VTuber・ゲーム曲 | F3 | 同上（VTuber・ゲーム曲） |
| M4 | アニメ作品 | F4 | 同上（アニメ作品） |
| M5 | 既存画像の再検査 | F5 | 候補一覧をオーナーが確認し、GO 分を反映 |
| M6 | 一括取得 | F6・F7・F8 | 試し実行の確認 → GO → 全件処理が完走（または再開可能な状態で継続中） |
